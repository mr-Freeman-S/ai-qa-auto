# Выполнение команд регресса

Работай в текущей сессии через подключённый Playwright MCP; не запускай вложенный Claude Code,
start.sh или run.sh. Команда пользователя задаёт новый набор проверок вместо прошлого задания.
Роль задаёт команда /regress_<роль>; корневая папка отчёта — из стартового сообщения сессии.
Аргументы команды уточняют раздел, тестовые данные и точку продолжения. В одном чате можно
по очереди запускать команды разных ролей: каждая сбрасывает браузер и входит заново.

1. Прочитай config.json, navigation.md и этот документ. Источник выбранного набора указан в команде.
   Не загружай regression.md и все кейсы одновременно. Набор роли — suites/<роль>.md; читай по одному
   файлу cases/<ID>.md на строку набора и проверяй кейсы по одному.
   Общие проверки, перечисленные в наборе как закреплённые за sysadmin, здесь не выполняй.
   Это исключение из области проверки, не PASS и не SKIPPED под текущей ролью.
   Не добавляй их обратно из regression.md или полного списка cases/. Прямой явный запрос
   конкретного исключённого ID допускает повторную проверку. Полный регресс требует
   отдельно выполнить общие проверки владельца; его FAIL/BLOCKED не превращается в PASS.
2. В начале КАЖДОГО вызова /regress_<роль> выполни browser_close,
   затем открой сайт заново: MCP работает с --isolated и создаёт чистую сессию.
   Следуй разделу «Вход: обязательный порядок действий» в navigation.md.
   Если MCP вернул ссылку на snapshot, сначала прочитай файл; не угадывай target.
   Для входа не используй evaluate/run_code и не генерируй JavaScript.
   Обязательно войди с секретами роли команды: QA_<РОЛЬ>_LOGIN / QA_<РОЛЬ>_PASSWORD. Существующую авторизацию
   не используй. Значения подставляет Playwright через --secrets в browser_fill_form/browser_type.
   Не читай .env, не проси пароль повторно и не печатай его. Если после сброса контекста
   форма входа отсутствует, поставь BLOCKED вместо использования неизвестной сессии.
   После одной неудачи входа остановись. MFA/SSO/CAPTCHA требуют участия пользователя.
   Между кейсами одной команды сессию не сбрасывай. «Посмотреть как» не заменяет роль.
3. Прочитай report-format.md. Итог — один results.md в корневой папке отчёта текущей сессии.
   После каждого кейса вызови Write или Edit для results.md, затем Read того же файла.
   Проверь наличие ID, статуса и фактического результата; текст в чате файл не обновляет.
   Без успешного Read не утверждай, что отчёт сохранён. Следующие команды дополняют тот же файл.
   Не создавай отдельные подкаталоги с отчётами для каждой команды и отдельный progress.md.
   Подробности ошибок и точку продолжения записывай в results.md.
   Скриншоты без явного запроса пользователя не создавай; доказательства описывай текстом.
4. GRID: каждая строка набора «GRID-NN × Таблица» — отдельная проверка этой таблицы; список таблиц
   уже отфильтрован по роли в roles.json. Неприменимые варианты помечай SKIPPED с причиной, не PASS.
   Один ID в одной таблице не покрывает остальные.
5. Тестовые данные: тесты САМИ создают и меняют то, что нужно кейсу. Отсутствие fixtures — не причина BLOCKED.
   a) Создание разрешено всегда. Имена — с префиксом и меткой прогона: «QA-AUTO <ММДД-ЧЧММ> <что>»;
      идентификаторы/username — `qa-auto-<ммдд-ччмм>-<что>`; email — `<username>@example.invalid`
      (письма на такие адреса не доставляются). Метку прогона задай один раз в начале команды.
   b) Менять, публиковать, архивировать, переносить, удалять, деактивировать разрешено ТОЛЬКО сущности
      с префиксом QA-AUTO / qa-auto (созданные тестами, в т.ч. в прошлых прогонах) и сущности,
      явно перечисленные в fixtures.local.md. Чужие существующие данные стенда не трогай.
   c) Действия «над собой» (снять себе роль, удалить себя из команды, деактивировать себя) выполняй только
      в QA-AUTO-команде/сущности, где тестовая учётка состоит специально для этого, — не в рабочих командах.
      Добавлять тестовые учётки ролей в QA-AUTO-команды разрешено.
   d) Предусловия, которые роль сама создать не может (группа, публикация формы, прикрепление ПО,
      доступ старшего, выдача ссылки исполнителю и т.п.), готовь шагом SETUP: browser_close, вход под
      QA_SYSADMIN_LOGIN / QA_SYSADMIN_PASSWORD, создание/настройка QA-AUTO-сущностей, browser_close,
      повторный вход под ролью команды. Проверку выполняй только под ролью команды; SETUP не является проверкой.
   e) Перед созданием посмотри fixtures.auto.md: если подходящая QA-AUTO-сущность уже есть — используй её.
      Если fixtures.auto.md нет — создай его с таблицей. Каждую созданную/изменённую сущность сразу дописывай в fixtures.auto.md (тип, имя, ID, состояние,
      кто/для какой роли, в каком кейсе) и в раздел «Созданные и изменённые сущности» results.md.
   f) Уборка в конце команды: архивируй/деактивируй QA-AUTO-сущности, не нужные следующим ролям
      (формы, ПО, команды, внешних пользователей); общие предусловия для других ролей оставь и пометь
      в fixtures.auto.md как «оставлено для …». Ничего, кроме QA-AUTO, не восстанавливай и не удаляй.
   g) BLOCKED допустим только если предусловие невозможно создать даже под сисадмином
      (приёмник webhook, визуальная проверка, неоднозначное требование) — укажи, что именно нужно.
   Не проси подтверждения каждого клика.
6. PASS требует подтверждения всех условий выбранной роли/таблицы. Не проверенные условия перечисляй.
   Скрытая кнопка не доказывает запрет прямой ссылки. FAIL — наблюдаемое расхождение,
   AGENT_ERROR — сбой инструмента или две неудачные одинаковые попытки. При общей недоступности
   сайта/модели останови прогон и сохрани точку продолжения. Не объявляй непройденные кейсы успешными.
7. FRM-03/FLC-06: условие удаления неоднозначно. Проверь на QA-AUTO-формах оба варианта
   (без ответов, но с полями; без полей и ответов), опиши фактическое поведение; статус ставь по
   фактическому поведению с пометкой «трактовка требует уточнения». ANS-05: нужен приёмник webhook. Визуальные и временные проверки требуют соответствующих доказательств.
8. Для /regress_<роль> после текущего раздела переходи к следующему без дополнительного согласования.
   Проверяй ветку ожиданий своей роли (см. «Фокус роли» в suites/<роль>.md); ветки других ролей не отмечай.
   Если контекст заканчивается, сохрани точную точку продолжения в results.md и сообщи пользователю,
   как продолжить из нового чата. Не пытайся держать весь регресс в контексте 4B-модели.
9. В конце дай число статусов и путь к отчёту. Полный прогон относится только к текущей роли;
   другие роли остаются непроверенными. Исходники кейсов не изменяй.
